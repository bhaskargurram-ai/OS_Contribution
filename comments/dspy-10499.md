Thanks — the review finding was right, and I've pushed a fix.

The original change treated two different failures the same way: a `list[int]` whose
content could not be parsed, and a value that parsed cleanly but is not a permitted member
of a closed set. Only the second is genuinely beyond the fallback's reach. Re-asking in
JSON can recover a malformed list, so suppressing the fallback there removed a working
recovery path.

It now classifies on the annotation. `Literal` and `Enum` name a fixed set of permitted
values, so a member violation propagates with the error naming what was expected.
Everything else keeps the previous behaviour and stays eligible for the fallback.
`XMLAdapter` is classified the same way.

Two tests cover both directions: a malformed `list[int]` still falls back to
`JSONAdapter`, and an `Enum` member violation does not.
